## 1. システム概要

### 1.1 システム名
Pure Rust AI Native CLI Development Kernel（纯 Rust AI Native CLI 開発カーネル）

### 1.2 システム定義
本システムは、Rust で実装された CLI/TUI ネイティブな開発カーネルであり、以下の 4 つの役割を兼ねる：

1. **スタンドアロン IDE**: 直接実行可能な開発環境
2. **Agent Runtime**: LangGraph 等の AI Agent の底層実行環境
3. **Local AI Compute Runtime**: ローカル AI 計算能力を提供
4. **Development Automation Kernel**: 開発自動化エンジン

### 1.3 システムの位置付け
**対象ではないもの**：
- Vim の替代品
- VS Code CLI 版
- AI チャット窓付き IDE
- LangGraph 専用ツール

**対象のもの**：
- マイクロカーネルアーキテクチャに基づく統一開発内核
- WASM Component と隔離 Native Worker による真の Plugin ホットスワップ
- Capability ベースの統一 API インターフェース
- Transaction セマンティクスを備えた Workspace 変更管理

---

## 2. 関連ステークホルダー

### 2.1 使用者
1. **Human Developer**: 直接 CLI/TUI で操作する開発者
2. **LangGraph Agent**: Python 上の LangGraph で実行される AI Agent
3. **Other Agent Framework**: 他の AI Agent フレームワーク（将来対応）
4. **CI System**: CI/CD パイプラインの自動実行
5. **Automation Engine**: イベント駆動の自動化ルール

### 2.2 運用者
1. **System Administrator**: Kernel デプロイと設定管理
2. **Plugin Administrator**: Plugin インストール・更新・削除
3. **Workspace Manager**: Workspace リソース管理

### 2.3 開発チーム
- **Kernel Core Team**: マイクロカーネル、Bus、Capability システム
- **Plugin Runtime Team**: WASM/Worker ランタイム実装
- **API Layer Team**: REST/JSON-RPC/MCP Adapter 実装
- **Local Compute Team**: 索引、グラフ、Context Compiler 実装

## 3. 機能要件（Functional Requirements）

### 3.1 コア機能要件（P0）

#### FR-001: マイクロカーネル
**要件**: Kernel Core は以下の基本機構のみを提供し、業務能力は Plugin を通じて提供される

- FR-001-01: Command Bus - すべてのアクション統一実行
- FR-001-02: Event Bus - プラグイン間通信
- FR-001-03: Capability Registry - 能力ベースのルーティング
- FR-001-04: Session Manager - マルチセッション管理
- FR-001-05: Transaction Manager - ワークスペース変更の原子性保証
- FR-001-06: Task Scheduler - INTERACTIVE/HIGH/NORMAL/BACKGROUND/IDLE による優先度制御
- FR-001-07: Plugin Manager - Plugin ライフサイクル管理
- FR-001-08: Security/Permission - ゼロトラスト権限モデル

**検証方法**: 
- Core のモジュール数が XX 以下であること
- 各機構が独立してテスト可能なこと
- 業務ロジック依存がないこと

---

#### FR-002: Buffer Engine
**要件**: ファイルシステムと独立した統一 Buffer 管理

- FR-002-01: Open/Read/Edit/Insert/Delete/Replace/Patch 操作
- FR-002-02: Undo/Redo スタック管理
- FR-002-03: Snapshot と Save 機能
- FR-002-04: 超大容量ファイル対応（Lazy Read, Chunk Read, Memory Mapping）
- FR-002-05: 複数エンコーディング対応（UTF-8, UTF-16, Shift-JIS, EUC-JP, GBK, BOM）
- FR-002-06: 複数改行符対応（LF, CRLF, CR）保留

**検証方法**:
- 1GB ファイルを開いて編集でき、Resident Memory が 100MB 以下
- Undo/Redo が正確に動作
- 保存後に元の改行符が保留される

---

#### FR-003: コマンド実行モデル
**要件**: すべてのアクションを統一 Command として実行

- FR-003-01: 標準 Command 構造（name, version, arguments, actor, session, permissions, timeout, metadata, cancellation_token）
- FR-003-02: Command 発見インターフェース（command.list で動的クエリ）
- FR-003-03: Command パイプライン対応（結果の構造化処理）
- FR-003-04: Side Effect 宣言（READ_ONLY/LOCAL_STATE/WORKSPACE_MUTATION/PROCESS_EXECUTION/NETWORK/DESTRUCTIVE）
- FR-003-05: Command 取消対応

**実装例**:
```
search "TODO" | filter "priority:high" | open
```

**検証方法**:
- 新規 Command が自動的に agent に発見可能
- Pipeline 中間結果が構造化データ
- Cancellation が effective

---

#### FR-004: Capability モデル
**要件**: Plugin を直接呼び出さず、Capability ベースで呼び出し

- FR-004-01: Capability 登録・発見インターフェース
- FR-004-02: Capability ルーティング（Priority/Policy/Availability/Performance に基づく Provider 選択）
- FR-004-03: Provider ホットスワップ（実装切り替え、Agent 無感知）
- FR-004-04: 標準 Capability 集合定義

**標準 Capability 例**:
```
text.search, text.regex, language.parse, language.symbol, 
language.definition, language.reference, git.status, git.diff,
debug.attach, test.run, ai.embed, ai.rerank, ai.complete, 
context.compress
```

**検証方法**:
- Capability Provider を動的に切り替え可能
- Agent が Provider 変更を認識しない
- ルーティングポリシーが正確に適用

---

#### FR-005: Session モデル
**要件**: グローバルな「現在の状態」を禁止し、Session スコープで管理

- FR-005-01: Session 属性（session_id, workspace_id, actor, permissions, active_buffers, active_transaction, resource_budget, context_budget, worktree, metadata）
- FR-005-02: Actor タイプ（Human, LangGraph, AI Agent, CI, Plugin, Automation）
- FR-005-03: マルチセッション同時実行
- FR-005-04: Session リソース隔離

**検証方法**:
- 複数 Session が同時実行でき、互いにカーソル・Transaction を污染しない
- Session ごとに独立した権限・予算が適用

---

#### FR-006: Transaction モデル
**要件**: ワークスペース修正を Transaction でラップ

- FR-006-01: Transaction ライフサイクル（NEW → ACTIVE → VALIDATING → COMMITTED または ROLLING_BACK → ROLLED_BACK）
- FR-006-02: Patch ベースの修正（整個ファイル書き込み禁止、expected_version/before_hash による競合検出）
- FR-006-03: Optimistic Concurrency（version/hash 検証）
- FR-006-04: Rollback 機能

**標準フロー**:
```
transaction.begin → file.patch → file.patch → test.run 
→ git.diff → transaction.commit
```

**検証方法**:
- Patch が version/hash 検証で競合を検出
- Rollback で元状態に復帰
- Crash Recovery で未完了 Transaction 復元

---

#### FR-007: Plugin ランタイム
**要件**: WASM Component と隔離 Native Worker の 2 層 Plugin 実行

**Runtime A: WASM/WASI Component**
- 用途: Formatter, Parser 補助, Text Transformer, Lint Rule, Small Tool
- 特性: Sandbox, Stable Boundary, Hot Load/Unload, Permission Control
- State: DISCOVERED → INSTALLED → VERIFIED → LOADED → INITIALIZING → ACTIVE → SUSPENDED → DRAINING → UNLOADING → UNLOADED （異常: FAILED, QUARANTINED）

**Runtime B: Native Worker**
- 用途: LSP, Debugger, Compiler, GPU, LLM, Embedding, Database, Large Indexer
- IPC プロトコル: stdio JSON-RPC
- 特性: Isolation, Crash Detection, Restart, Disable

**検証方法**:
- WASM Plugin の Hot Load/Unload が正常動作
- Native Worker Crash が Kernel に影響しない
- Plugin Manifest の Capability 宣言と実装が一致

---

#### FR-008: イベント駆動アーキテクチャ
**要件**: すべてのプラグイン間通信は Event Bus 経由

- FR-008-01: 統一 Event Envelope（event_id, sequence, type, timestamp, workspace_id, session_id, execution_id, actor, payload）
- FR-008-02: Event 分類（Transient vs Durable）
- FR-008-03: 標準 Event 集合（WorkspaceOpened, FileOpened, BufferChanged, FileSaved, TransactionStarted, PluginLoaded, CommandStarted, CommandCompleted 等）

**検証方法**:
- Event stream から完全な Replay 可能
- Audit trail から source 追跡可能
- Monitoring で全 Event observable

---

#### FR-009: 4 つの実行モード
**要件**: Kernel が 4 種類の起動モードで動作

**5.1 Standalone IDE Mode**
```bash
kernel . 
# または
kernel edit .
```
- TUI で直接操作、Network 不要

**5.2 Headless Server Mode**
```bash
kernel serve
```
- HTTP/SSE/WebSocket/JSON-RPC/MCP Adapter で外部利用

**5.3 Local IPC Mode**
- LangGraph → stdio JSON-RPC → Rust Kernel
- Unix Socket (Linux/macOS), Named Pipe (Windows)

**5.4 Embedded Rust Mode**
```rust
use kernel_core::Kernel;
```
- 他の Rust Application に Library として埋め込み

**検証方法**:
- 各モードが独立して動作確認
- Mode 間の状態・API 一貫性確認

---

#### FR-010: Vim 編集モデル
**要件**: Vim 編集パラダイムを実装

- FR-010-01: Normal/Insert/Visual/Command モード
- FR-010-02: Operator/Motion/Text Object/Register/Macro/Repeat
- FR-010-03: Command History/Search History

**拡張 Mode**:
- AI Mode, Review Mode, Diff Mode, Debug Mode
- ※ Mode ≠ Core Business Logic（Plugin で実装）

**検証方法**:
- キーバインディングが Vim と一貫
- Macro 記録・実行が正確

---

#### FR-011: 検索エンジン 3 層構造
**要件**: テキスト・構造・意味検索を段階的に実行

**層 1: テキスト検索**
- Exact, Case Sensitive/Insensitive, Regex, Glob, Grep

**層 2: 構造検索**
- AST, Symbol, Definition, Reference, Call Site

**層 3: 意味検索**
- Embedding, Vector Similarity, Rerank, Code Intent

**Streaming 要件**:
- 大規模検索は結果を逐次返却（SearchStarted → Match → Match → Progress → SearchFinished）

**検証方法**:
- 100 万ファイル検索が Streaming で可能
- 結果の正確性が層別に検証

---

#### FR-012: Context Compiler
**要件**: Repository → Agent Context への圧縮パイプライン実装

**処理流れ**:
```
Repository → Index → Symbol → Dependency Graph → Relevance 
→ Diff → Dedup → Rerank → Summary → Token Budget → Agent Context
```

**Context Strategy**:
- fast: Search/Symbol/AST
- balanced: Search/AST/Graph/Rerank
- deep: Search/AST/Graph/Embedding/Rerank/Local SLM
- local_only: Remote AI 禁止

**検証方法**:
- 100,000 Token Context を 10,000 Token に圧縮で実行
- 圧縮理由が明示（direct reference/caller dependency/related test 等）

---

#### FR-013: Local Compute パイプライン
**要件**: AI タスクを 5 段階で処理

**Level 0**: 確定的算法
- Hash, Diff, Regex, Parser, AST, Symbol, Call Graph

**Level 1**: Index/Graph
- Index, Graph Query, Static Analysis, History, Cache

**Level 2**: Embedding/Rerank
- Embedding, Semantic Search, Rerank, Clustering

**Level 3**: 本地 Small Language Model
- Classification, Intent Routing, Context Summary, Code Ranking

**Level 4**: Remote Large Language Model
- Complex Reasoning, Architecture, Large Refactor, Complex Generation

**検証方法**:
- 各 Level で処理が正確に完結
- Remote AI 不要タスクが Local で完結率 > 80%

## 4. 非機能要件（NFR）

### 4.1 性能要件

#### NFR-001: 起動パフォーマンス
**要件**: Kernel を初期化してから TUI Ready まで
- **目標**: ≤ 150 ms（参考開発機）
- **前提**: 索引・AI モデルは Lazy Load
- **検証方法**: 冷起動タイムを計測

#### NFR-002: Core Idle Memory
**要件**: Kernel Core がアイドル時のメモリ
- **目標**: ≤ 50 MiB
- **検証方法**: `ps` で RSS メモリ確認

#### NFR-003: 入力イベント応答
**要件**: キー入力から画面更新までのレーテンシ
- **目標**: P99 < 16 ms（常規入力）
- **制約**: AI 待機は絶対禁止
- **検証方法**: Event Loop Profiling

#### NFR-004: Local IPC オーバーヘッド
**要件**: stdio JSON-RPC による IPC 遅延
- **目標**: P95 < 10 ms
- **検証方法**: RPC Benchmark

#### NFR-005: 検索パフォーマンス
**要件**: 100 万ファイルの Text Search
- **目標**: < 5 秒（Streaming 開始）
- **検証方法**: Benchmark Suite

#### NFR-006: Context 圧縮パフォーマンス
**要件**: 100,000 Token → 10,000 Token 圧縮
- **目標**: < 2 秒（ローカル処理）
- **検証方法**: Benchmark Suite

### 6.1 アーキテクチャ禁止事項

```
❌ TUI → Git
```

**禁止 3**: Plugin A が Plugin B Object を保持

**禁止 5**: AI が整個 Repository 書き直し
```
✓ Patch ベース修正のみ
```

**禁止 6**: 複数 Agent が Global Workspace State 共有

**禁止 7**: Plugin が全 FS/Network Permission 所持

**禁止 8**: すべてのモデルが Main Process に常駐

**禁止 9**: Rust dylib が唯一 Plugin ABI

**禁止 10**: TUI がシステム固有の業務ロジックを所持

## 10. リスク・制約

### 10.1 既知リスク
1. **Plugin ABI 安定性**: Rust dylib は ABI 不安定のため WASM 優先【対策】WASM Component Model 採用
2. **Performance 達成**: Startup 150ms 目標達成 Hard【対策】Lazy Load + Profiling
3. **Crash Recovery**: Kernel Crash 時のデータ一貫性【対策】Journal-based Recovery
4. **Multi-agent Conflict**: Session 隔離不十分【対策】Session Scoped リソース設計
