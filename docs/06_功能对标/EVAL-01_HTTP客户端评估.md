# [EVAL-01] 高速版 HTTP 客户端架构评估: 系统 curl vs ureq+rustls

> 对应 WBS-03 工作包 **O4.3**。
> 评估对象: `ide-fast` 中的网络调用 (AI 对话流、GitHub 插件下载、检查更新/自更新)。
> 结论: **保持系统 curl 子进程方案, 不引入 ureq+rustls**。

---

## 1. 现状与调用特征

高速版当前有三处网络功能:
1. **AI 对话** (`ide-fast/src/ai/transport.rs`): SSE 流式返回, 传输走 `curl -sS -N -K -` (密钥与请求体通过 stdin 注入, 不泄露至命令行)。
2. **GitHub 插件下载** (`ide-fast/src/ghplugin.rs`): 下载 tarball / zip / manifest, 严格校验域名前缀与重定向次数。
3. **检查更新与包下载** (`ide-fast/src/updnet.rs`): 下载 `SHA256SUMS.txt`、`.sig` 及安装包, 带有硬性超时与大小上限。

三处特征共同点:
- **低频触发**: 仅在用户主动点击「检查更新」、「安装插件」或触发「AI 对话」时运行, 编辑器主循环、启动首帧期间完全不发生网络调用。
- **严格安全沙箱**: 全面开启 `--proto =https --proto-redir =https`, 限制最大重定向次数 (0~5), 限制单次传输大小与连接超时。

---

## 2. 方案对比与实测数据

| 维度 | 方案 A: 系统 `curl` 子进程 (现状) | 方案 B: 引入 `ureq` + `rustls` | 差异与影响 |
|---|---|---|---|
| **exe 二进制体积** | **17.79 MB** (Release 构建) | 预计 **19.8 ~ 20.5 MB** (+1.8 ~ 2.5 MB) | Rustls、webpki-roots 及加密后端 (ring/aws-lc) 显著膨胀体积 |
| **MSI 安装包体积** | **7.11 MB** | 预计 **8.2 ~ 8.6 MB** (+15% 膨胀) | 高速版以轻量小巧为核心优势 |
| **首帧耗时与启动内存** | **0 开销** (网络栈不在主进程) | 网络初始化虽可惰性加载, 但增加代码段映射 | 违背 CODING-STANDARDS §0.3 轻量原则 |
| **操作系统支持** | Windows 10 (1803+) / Windows 11 全内置; Linux/macOS 默认自带 | 纯 Rust 实现, 无外置依赖 | 目标用户环境 100% 存在 `curl.exe` |
| **证书与系统代理** | 自动支持系统根证书库与企业网络环境 | 需额外引入 `rustls-native-certs` 或打包 `webpki-roots` (遇到自签 CA/代理容易失败) | curl 的代理穿透与网络兼容性更强 |
| **安全性** | 密钥走 stdin (`-K -`), 不进命令行参数; 参数严格限制协议 | 内存中持有密钥, 进程内解析 TLS | 两者相当; curl 进程隔离甚至具备更佳的故障隔离 (crash 不影响主编辑进程) |

---

## 3. 架构结论

1. **维持当前架构**: 高速版定位于极致速度、低内存和极小分发体积。系统 `curl` 子进程方案不占用主进程常驻内存, 隔离性好, 免除了在 Rust 二进制中打包庞大 TLS 引擎与证书数据库的沉重代价。
2. **后续演进建议**: 保持现有 `Transport` 与 `Fetch` 特征抽象, 若未来跨入不支持 curl 的极特殊嵌入式受限环境, 再通过 feature 条件编译提供原生实现, 目前不进行依赖替换。
